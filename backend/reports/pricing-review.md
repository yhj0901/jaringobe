## store 경로 확인

`mealplan.service._price`는 `DBPriceProvider`만 호출한다. `store.service.build_cart`의 네이버 검색 결과는 장바구니/주문 preview의 별도 가격이며 `meal_ingredients.est_cost`, `meal_plans.total_cost` 또는 `ingredient_price_refs`를 갱신하지 않는다. 따라서 네이버 키를 채워도 현재 구조에서는 식단 생성 예산 판정에 store 가격이 반영되지 않는다.

`store.naver.search_candidates`는 키가 없으면 외부 호출 없이 빈 후보 목록을 반환한다. `store.service.build_cart` 및 `order.service._build_preview`는 키 부재를 `PRICE_LOOKUP_UNAVAILABLE`로 알리고, 주문은 미매칭 품목을 유지한다. 이번 작업은 store 연결을 추가하거나 이 경로를 변경하지 않는다.

## 구현 정책과 시드 범위

`pantry_prices.py`의 무료 물 집합과 5종 양념 추정치를 폴백 및 시드가 공유한다. 이들은 DB 초기화 누락 시에도 비용이 폭증하지 않아야 하므로 코드에 두고, 일반 40종 재료의 지역별 추정치는 `price_catalog.py`를 통해 테이블에 명시적으로 넣는다. 서버 시작/요청 중 자동 INSERT는 없으며, GET 부작용이나 암묵적인 운영 DB 쓰기를 추가하지 않는다.

DB 기준가(name, region, unit, currency 일치 및 pack_qty > 0)가 최우선이다. 무료 정책은 기준가가 없을 때 적용하므로 운영자가 명시적으로 가격을 등록하면 그 값을 존중한다. 양념에는 기존 100원/0.20 USD 최소 금액 및 8,000원/9 USD 상한을 적용하지 않고 사용량에 비례하여 Decimal로 계산·소수 2자리 반올림한다. 물/양념 이름은 공백·영문 대소문자를 정규화한 정확한 별칭으로 판정하고 부분문자열은 사용하지 않는다. 일반 DB 조회는 기존 정확한 이름·단위 매칭을 유지한다.

| 기본 양념 | KR 초기 추정 | US 초기 추정 | 모호한 단위 1회 사용량 |
|---|---:|---:|---:|
| 소금 | 2,200원/1kg | 2 USD/1kg | 1g |
| 후추 | 5,400원/50g | 2 USD/50g | 0.1g |
| 설탕 | 2,400원/1kg | 2 USD/1kg | 4g |
| 식용유 | 6,800원/1.5L | 5 USD/1.5L | 5ml |
| 참기름 | 8,500원/320ml | 7 USD/320ml | 3ml |

US 값은 현지 실측 자료를 확보한 가격이 아니라 합리적 소포장 규모의 자체 추정치이며 환율 변환도 아니다. 물은 KR/US 모두 조리용 수도 비용을 제외한다. 알려진 양념의 kg/L 단위는 1,000배, tsp/tbsp는 5/15g·ml, pinch는 0.3g·ml로 근사한다. g↔ml의 밀도는 1로 단순화했고 ea/약간/알 수 없는 단위는 표의 1회 사용량 × 수량으로 계산하므로 정밀 계량이나 완제품 한 병의 구매액을 의미하지 않는다. 일반 미등록 재료의 기존 난수 근사는 남아 있다.

KR 시드는 40종 외 후추·참기름, 한·영 별칭 및 규칙 생성기에서 쓰는 두부/애호박/양파/대파/감자/당근 ea 변형을 포함한다. 자세한 각 항목의 포장량·가격·근거(A/B/E)는 `price_catalog.py`에 있다. US 일반 재료 시드는 이번 범위에 없고 US 기본 양념은 코드 폴백으로만 제공한다.

## 실행 명령 및 후속 적용

백엔드 디렉터리에서 실행한다. 기존 테이블이 이미 존재해야 하며 이 스크립트는 DDL을 수행하지 않는다. `DATABASE_URL`은 셸에서 명시해야 하고 `--database`와 URL의 DB 이름이 다르면 연결 전에 거절한다. 기존 행은 unique(name, region, unit) 충돌 시 보존하고 전체 작업을 한 트랜잭션으로 커밋한다. 따라서 향후 카탈로그 숫자만 바꿔 재실행해도 기존 가격은 갱신되지 않으며 별도의 검토된 가격 갱신 절차가 필요하다.

```bash
DATABASE_URL='postgresql+asyncpg://jaringobe:jaringobe@localhost:5433/jaringobe_pricing' uv run pytest --cov=app
DATABASE_URL='postgresql+asyncpg://jaringobe:jaringobe@localhost:5433/jaringobe_pricing' uv run python -m app.domains.mealplan.seed_prices --database jaringobe_pricing
DATABASE_URL='postgresql+asyncpg://jaringobe:jaringobe@localhost:5433/jaringobe_pricing' uv run python scripts/reprice_snapshot.py --database jaringobe_pricing --snapshot reports/pricing_snapshot.json
uv run ruff check app tests scripts
uv run mypy app
```

기존 pytest fixture는 전용 DB의 public 스키마를 매 테스트마다 재생성하므로, 지속적으로 남길 시드는 모든 테스트 종료 후 마지막에 실행한다.

이 워크트리에서 uv의 `UV_PROJECT_ENVIRONMENT`는 외장 디스크의 `/Volumes/Development/App/.development/venvs/jaringobe-pricing`을 사용했다. 재계산 스크립트는 PostgreSQL 세션을 읽기 전용으로 열며, 원본 JSON의 개별 사용량을 수정된 provider에 통과시킨다. 기본 재료 최소값 때문에 합산 후 한 번 계산하는 방식과 값이 달라질 수 있어 104개 행을 각각 계산한다.

운영 DB에는 시드를 적용하지 않는다. 코디네이터가 변경 코드를 통합하고 별도 승인된 운영 적용 절차에서 이 스크립트의 대상 DB를 바꿔 실행해야 일반 40종 기준가가 실제 서비스에 반영된다. 기존 저장 식단 원가·상태는 자동 갱신하지 않으므로 새 코드/시드만 배포해도 이미 저장된 over_budget가 바뀌지 않으며, 별도로 승인된 재생성이 필요하다. 배포/서버 재시작/기존 식단 갱신은 이번 작업에서 수행하지 않는다.
