## P0-2: 진단 정정 및 원인

코디네이터가 초기 진단을 정정했다. 반복 6종과 재료 합집합 15종은 `_RECIPES['KR']` 폴백과 정확히 일치한다. 폴백은 냉장고 힌트를 읽지 않으므로 기존 12/15=80%는 되먹임 효과의 기준선으로 사용하지 않았다.

유료 진단 3회 결과:

| 조건 | 시간 | 결과 |
|---|---:|---|
| 원본 생성기/LLM 래퍼 | 60.18초 | APITimeoutError → 폴백 |
| 간결한 객체 JSON 지시 | 60.06초 | stop_reason=max_tokens, output_tokens=8000 → JSONDecodeError → 폴백 |
| 위치 배열 압축, 기본 effort 유지 | 60.13초 | APITimeoutError → 폴백 |

모두 폴백 21끼·6종·142,404.20원을 재현했다. 과거 단일 사고의 정확한 예외는 로그가 없어서 소급 확정할 수 없지만 현재 조건에서 시간/출력 상한 두 실패를 직접 재현했다.

설정 모델은 `claude-sonnet-5`다. [Anthropic 공식 마이그레이션 가이드](https://platform.claude.com/docs/en/models/sonnet-5/migration-guide)에 따르면 adaptive thinking이 기본 ON, effort가 기본 high이며 추론 토큰도 max_tokens에 포함된다. 코드가 이 변경을 고려하지 않고 60초/8000 토큰으로 호출하고 있었다. [effort 문서](https://platform.claude.com/docs/en/build-with-claude/effort)는 응답 토큰 지출/지연을 줄이는 조절값을 설명한다. 개별 실패 호출의 추론 토큰 수는 측정하지 않았으므로 추론만이 모든 토큰을 소비했다고 단정하지 않는다.

수정:

1. Sonnet 5 요청에 `output_config.effort=low`를 명시한다. 미지원 모델에는 보내지 않는다.
2. LLM 내부 JSON을 위치 배열로 압축하고 기존 draft 객체로 복원한다. 기존 객체 응답도 수용하며 외부 식단 필드 계약은 유지한다. 조리 설명 길이만 제한하고 재료 전체 수량은 유지한다.
3. 최초 호출부터 호출자가 전달한 날짜별 안분 예산을 prompt에 포함한다. 예산 계산식이나 accrued−confirmed 주문 한도 로직은 수정하지 않는다.
4. 60초 호출 상한, SDK 재시도 0회, 서비스 재시도 진입 예산 25초는 유지한다.
5. 예외 타입/안전한 오류 요약/HTTP 상태와 폴백 출처를 JSON `extra`로 로깅한다. 성공 응답도 stop_reason/output_tokens/elapsed를 기록한다. SDK 예외 원문·traceback에는 요청 본문이 섞일 수 있어 기록하지 않는다. JSON 파서 표준 오류 문구와 행/열, 타임아웃/HTTP별 요약으로 진단한다.
6. 동일 메뉴 반복 상한 등 다양성 제약은 추가하지 않았다. 실측상 그런 문제는 재현되지 않았다.

## 영속 출처 / 출력 상한 / 최종 회귀

인프라 커밋 `7c4ccd2`를 요청대로 `d2ce57f`로 cherry-pick했다. 이는 인프라가 작성한 `0013_mealplan_generation_source` 및 모델/문서 변경이며 이 워커가 신규 DDL을 작성한 것이 아니다. 기존 metadata 기반 테스트가 Alembic 버전 테이블을 제거하므로 전용 DB에 0012 stamp 후 전달된 0013 upgrade를 적용했다. 인프라가 검증한 upgrade/downgrade 왕복은 반복하지 않았다.

- `GenerationSource` enum에 허용값 `llm|fallback`을 한 곳에서 정의했다.
- `MealDrafts`의 요청별 출처를 최종 채택 결과와 함께 `meal_plans.generation_source`에 저장한다. 재생성 접수 시 기존 출처를 비워 이전 결과를 새 작업의 출처로 오인하지 않게 한다.
- 모델 validator가 알 수 없는 값의 생성/대입을 거부한다. 기존 미상 행 NULL은 유지한다.
- GET 상세/latest의 `generationSource`는 `llm|fallback|null`이며 202 접수 응답 구조는 유지한다.
- `stop_reason=max_tokens`는 파싱 가능한 부분 JSON이어도 `LLMOutputLimitError`로 처리한다. 오류 로그에 stop_reason과 타입을 남기고 최종 source는 fallback이다. 14일×3끼 사례를 네트워크 없는 회귀 테스트로 확인했다.
- Sonnet 5에만 effort를 보내고 다른 모델에는 보내지 않는다. API가 옵션을 400으로 거부해도 오류 타입/HTTP 상태를 기록하고 source=fallback으로 정상 폴백한다.
- 최종 백엔드 전체 회귀: `469 passed`, coverage `94%` (3747 statements, 219 missed), 107.54초.
- `uv run ruff check app tests scripts/compare_loopfix.py` 통과, `uv run mypy app` 82개 소스 통과.
- 최초 전체 실행의 기존 `expiresAt is None` 기대 1건만 실패하여 변경된 계약에 맞췄고, 이후 전체 실행은 통과했다. 수정/검증 실패 10회 한도에 도달하지 않았다.
- 프론트 변경 없음. 설계/테스트 문서 직접 수정 없음; 인프라 전달 커밋의 문서 변경만 포함.

추가 잔여 위험:

- API는 최대 31일×5끼=155끼를 허용한다. 품질 보완 표본 21끼/4069 토큰의 단순 비례 추정이면 93끼 약 18000, 155끼 약 30000 토큰이며 60초도 초과할 수 있다. 이는 큰 식단을 실제 호출한 결과가 아니라 추정이다. 상한만 올려 시간을 우회하지 않았고, 크기 제한/타임아웃 재설계/분할 생성은 지시대로 구현하지 않았다. 출력 초과는 이제 명시적 로그와 fallback 출처로 드러난다.
- 카레가루·국간장은 현재 가격 카탈로그에 없어 올바로 주문 재료에 포함돼도 미등록 근사 원가를 사용한다. 이번 범위에서는 가격 카탈로그를 수정하지 않았다.
- upstream이 없는 작업 브랜치여서 `git pull --ff-only`는 tracking 정보 없음으로 종료했다. 지정된 기준/현재 브랜치를 유지했으며 임의 upstream 설정이나 다른 브랜치 병합은 하지 않았다.

medium 표본에서 카레가루·국간장·대파처럼 **조리법에 명시된 재료**가 목록에서 빠지는 사례는 직접 대조상 사라졌다. 다만 시금치나물비빔밥/콩나물무침밥의 데침물, 후라이용 기름처럼 조리 과정에 필요한 모든 전제 재료가 완전히 명세된 것은 아니다. 재료 조합·조리 단계는 앞선 low 표본보다 구체적이지만 프롬프트·effort만으로 주문 목록/조리법 일관성을 보장할 수 없다는 한계는 남는다.

지연은 같은 prompt의 low 대비 29.16초 증가했고 출력 토큰은 3361개 증가했다. 60초 상한까지 여유는 6.90초이므로 안정적인 타임아웃 회피를 보장하지 않는다. 추가 high 호출/프롬프트 확장/상한 인상은 하지 않았다. 완전한 일관성 검증·수리, 큰 식단 분할 등 구조적 처리는 코디네이터의 별도 작업으로 남긴다. 코디네이터 결정으로 최종 effort는 low를 유지한다. medium 53.10초는 서비스 재시도 진입 예산 GENERATION_TIME_BUDGET_SECONDS=25를 초과하므로 이 표본의 첫 호출 후 알레르기 위반 재시도를 시작할 수 없다. 같은 최종 prompt의 low 23.94초는 재시도 진입 여유를 남겼다. 다만 다른 low 표본은 34.67초였으므로 low도 항상 25초 이내라는 보증은 아니다. medium은 부분적인 품질 개선을 위해 재시도 여유를 포기할 수 없어 채택하지 않았다.
