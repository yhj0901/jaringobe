# 식단 재료 충분성 보완 — 부분 개선

기준 `614633d`, 작업 브랜치 `yhj0901/수정-재료일관성`. 코디네이터가 이 외장 워크트리에서 구현·커밋하고 자신이 통합하도록 승인했다. 운영 서버 재시작·운영 데이터 변경·새 마이그레이션·프롬프트 강화·effort 변경·추가 hot-path LLM 호출은 하지 않았다.

## 채택한 방식

`generator.generate_meals`의 LLM/폴백 결과에 결정론적 보완을 적용한 뒤 기존 알레르기 검사 → 가격 → 예산 → 저장 경로를 따른다. `IngredientRepairs`는 실제 보완 내역과 알레르기로 추가하지 못한 필수 재료를 별도로 전달하며, `MealDrafts`가 후자를 호출별로 보존하고 `service._check_allergies`가 기존 위반 목록에 합친다. 외부 응답 필드·DB 스키마는 바뀌지 않는다.

판정은 가격 별칭이 아닌 별도의 조리 사전과 공정 규칙을 사용한다. 카레의 분말/물, 볶음·프라이의 팬 기름, 국·찌개의 액체, 조림·달걀찜·죽의 물, 생쌀 취사 물, 면 삶는 물, 알려진 나물의 데침물을 인원 수로 산정한다. 제목뿐 아니라 steps에 명시된 반찬과 재료도 보조 신호로 읽는다. 물의 공정별 수요는 합산하고 국물용 육수로 데침물을 충당했다고 간주하지 않는다. 기존 양을 줄이지 않고 알려진 품목의 0/음수 수량도 누락처럼 보완한다. 기존 이름을 유지하며 두 번 실행해도 더 늘어나지 않는다.

수량은 전문 조리 검증치가 아닌 명시적인 초기 조리 가정이다. 예를 들어 국물 300ml/인, 카레분 25g/인과 분말 g당 물 7ml, 팬 기름 5ml/인, 데침물 최소 1L 또는 500ml/인, 생쌀 g당 취사 물 1.5ml이다. 양수로 적힌 모든 재료의 충분한 1인분을 보증하지는 않는다. 기호 양념 전부를 의무로 늘리지 않는다.

완성 카레소스, 생무침/샐러드, 기존 식용유·버터, 에어프라이/기름 없는 조리는 분리한다. 중간 검토에서 발견한 `콩나물` 재료명과 `나물` 조리법의 충돌은 재료 토큰을 공정 판정에서 분리했고, `볶음탕` 접미사는 팬 볶음과 구분했다. 특정 완성 요리명에 대한 제외 목록은 0개이며, `콩나물`이라는 재료 토큰의 어휘 예외 1개와 완제품 카레 이름 집합은 유지한다. 요리군을 식별하는 명시 표제어(무국, 계란찜 등)는 유한한 사전이므로 새로운 요리에 일반화가 보장되지는 않는다.

## 알레르기 경로

코디네이터 정정 지시를 반영했다. 충돌 재료는 추가 전에 건너뛰며, 그 재료가 필요하다는 신호를 기존 알레르기 위반에 합쳐 원래의 재시도 경로로 보낸다. 상품별 배합을 보증할 수 없는 복합 양념/혼합유는 알레르기 입력이 있으면 자동 추가하지 않고 같은 경로로 보낸다. 로그는 `allergy_constraint`와 `unverified_composition`을 구분하되 건강 입력·재료명·프롬프트를 기록하지 않는다. 재시도 예산 소진 후 warning + ready/over_budget 저장은 기존 정책 그대로이며 안전상 잔여 위험이다.

## 실측 방법

`compare_ingredients.py --allow-paid-llm`로 Sonnet 5 low, 동일 `loopfix-input.json`(KR 2인, 7일 × 3끼, 예산 102,666.67원)과 동일 프롬프트를 사용했다. 키는 승인된 파일에서 필요한 값만 선택했고 DATABASE_URL은 명시한 `localhost:5433/jaringobe_ingcheck`만 허용했다. 기존 마이그레이션은 전용 DB에만 적용했으며 정상 기준가 시드 131행 → 보강 시드 160행으로 측정했다.

총 유료 호출 10회: 수정 전 실패 1 + 정상 전 3 + 중간 후 3 + 최종 후 3. 당초 8회 제한은 코디네이터가 10회까지 승인했고, 추가 3회는 중간 식단 직접 검토에서 발견한 오탐을 교정한 뒤 다시 측정하기 위한 것이다. 실패·중간 결과도 별도 JSON으로 보존했다. 측정은 생성 함수 1회와 실제 가격 공급자를 사용하며, 유료 예산/알레르기 재시도까지 호출하는 API 종단 실험은 아니다. 그 연결은 무과금 서비스/DB 테스트로 검증했다.

자동 누락 수는 알려진 규칙에서 **이름이 없고 양도 없는 재료**를 끼니별로 센다. 0수량, 기존 재료/국물의 수량 하한 증액은 별도 지표다. 자동 수치가 0이어도 완전한 충분성 검증으로 해석하지 않으며 모든 결과 식단을 직접 읽었다. 재고 사용률은 기존 비교와 같은 `재고에 있는 사용 재료 종류 / 식단 사용 재료 종류`이며, 함께 `사용한 재고 종류 / 입력의 전체 재고 37종`을 기록했다. 수량 소진율이나 실제 배송 성공률이 아니다.

## 남은 누락과 한계

- 유한한 조리 사전 밖의 요리·재료·조리 전제, 익힌 재료와 생재료의 복잡한 별칭, 농축/희석 소스, 여러 요리를 합친 제목을 모두 해석하지 못한다. 미등록 요리를 검증됐다고 표시하거나 실패시키지 않는다.
- `간장양념`처럼 배합이 생략된 표현의 모든 구성과 `밥을 짓는다`인데 목록에는 완성 밥만 있는 조리 상태 불일치는 해결하지 않는다.
- 모든 양수 재료의 충분한 양, 균형 잡힌 한 끼, 영양·알레르기 안전을 이 사전이 보증하지 않는다. 예산을 맞추려고 기존 양을 줄이는 코드는 넣지 않았다.
- 추가하지 못한 필수 재료는 재시도 대상으로 들어가지만 기존 25초 예산이 지나면 경고가 붙은 식단으로 저장될 수 있다. low 호출 자체가 25초를 넘는 표본도 있어 알레르기 재시도 기회가 매번 보장되지는 않는다.
- 초기 전 실패 1회는 `end_turn`, 3,174 output tokens, 27.554초 뒤 폴백이었다. 출력 절단은 아니며 JSON 추출/위치 배열 파싱 계열 실패로 좁혀지지만 해당 첫 호출의 원문·예외 타입을 보존하지 못해 정확한 하위 원인은 미검증이다. 이후 호출부터 원문·안전한 예외 타입을 저장하며 파싱 동작은 수정하지 않았다.
