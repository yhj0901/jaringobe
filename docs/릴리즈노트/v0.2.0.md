# v0.2.0 릴리즈 노트

- 릴리즈 날짜: 2026-09-05 / 이전 버전: v0.1.0 (2026-07-09)
- 범위: **자동주문 P0 + 앱 웹뷰·푸시 알림 + 주간 자동 사이클(선순환 루프 완결)** — 브랜치 `feature/loop-cycle-base` (`origin/main` `efc8376` → `a6d9bef`, 비머지 커밋 41건 / 193 파일), QA GATE 4 재판정 통과 (Critical 0 / High 0 / Medium 0 / Low 5)
- 근거 문서: 기획 `docs/기획/자동주문-장바구니.md`·`docs/기획/루프완결-주간사이클.md`, 설계 `docs/설계/*.md` v1.6~v1.10, QA `docs/테스트/*.md` (2026-09-05 재판정)

> **버전 번호 근거 (v0.2.0)**: 1.0 이전이므로 SemVer 0.x 규약(minor 가 기능 추가와 호환성 파괴를 함께 담음)을 따른다. 이번 범위는 신규 도메인 2개(order·cycle·notification 포함 시 3개)와 DB 리비전 4개, 그리고 기존 계약을 깨는 변경(`GET /orders/latest` 확장, `GET /orders/preview` 의 `refresh` 제거)을 포함하므로 patch 가 아닌 **minor** 증가가 맞다. major(1.0)는 실결제·상시 호스팅이 없는 시뮬레이션 단계이므로 아직 아니다.
> 참고: v0.1.0 과 이번 범위 사이에 main 에 머지된 기능(온보딩·회원 홈·AI 식단·가상 냉장고·식사 완료·설정·스토어 연동 상태·지역 전환, PR #5~#38)은 **릴리즈 노트가 작성되지 않았다.** 본 노트는 그 기능들을 전제로 한 증분만 다룬다.
> 코드의 버전 문자열(`backend/pyproject.toml`·`backend/app/main.py`·`frontend/package.json`)은 아직 `0.1.0` 이다 — 문서 에이전트는 코드를 수정하지 않으므로 릴리즈 시 함께 올려야 한다(📋 알려진 이슈).

## ⚠️ Breaking Changes

### DB 마이그레이션 필요 — 리비전 `0009` → `0010` → `0011` → `0012`
`alembic upgrade head` (컨테이너 진입점이 자동 실행, `RUN_MIGRATIONS=false` 면 수동). 체인 `0008 → 0009_orders → 0010_notification_app → 0011_cycle_core → 0012_cycle_links`, `alembic heads` = `0012` 단일.

| 리비전 | 내용 |
|--------|------|
| `0009_orders` | `orders` + `order_items` 신규 (자동주문 P0 시뮬레이션 확정 스냅샷) |
| `0010_notification_app` | `device_tokens` · `notification_settings` · `notification_logs` · `app_login_codes` 신규 |
| `0011_cycle_core` | `user_cycle_settings` 신규, `orders` 컬럼 9종 추가·`status`/`frequency` CHECK 확장·`confirmed_at` NOT NULL 해제·**기존 confirmed 주문 백필**·부분 유니크 인덱스 2종·due 인덱스 2종 |
| `0012_cycle_links` | `fridge_items.order_id` FK + `source='order'→'delivery'` 통합, `users.last_seen_at`(+백필), `notification_settings.type` CHECK 에 3종 추가 |

- **★ 0011 백필 `inbound_at := confirmed_at` 이 없으면 냉장고 재고가 두 배가 된다.** 자동주문 P0 는 확정 즉시 냉장고에 넣었고, 이번 스케줄러의 등록 스캔은 `status='confirmed' AND inbound_at IS NULL AND delivery_eta <= now` 를 대상으로 한다. 백필이 빠지면 이미 들어간 주문을 다시 등록한다. 0011 은 이 백필(`cycle_start`·`delivery_eta`·`inbound_at`·`delivery_state='delivered'`)을 포함하며 QA M-01/M-02 에서 실데이터로 검증됐다(스캔 후보 0건). 적용 후 확인 쿼리:
  ```sql
  SELECT count(*) FROM orders WHERE status='confirmed' AND inbound_at IS NULL AND delivery_eta <= now();  -- 0 이어야 정상
  ```
- 0011 은 같은 사용자·사이클의 중복 confirmed 를 최신 1건만 남기고 나머지를 `cancelled` 로 강등한 뒤 부분 유니크 인덱스를 만든다(삭제하지 않음). 중복이 남아 있으면 마이그레이션이 예외로 중단된다.
- **0011 / 0012 의 downgrade 는 파괴적이다.** 0011 은 `confirmed_at` NOT NULL 복원을 위해 비확정 주문(`status <> 'confirmed' OR confirmed_at IS NULL`)과 연관 `order_items` 를 **삭제**하고, 0012 는 신규 알림 설정 3종 행을 삭제하며 `source` 를 `order` 로 되돌린다. 운영 DB 롤백 전 손실 행 수를 먼저 확인할 것 (`docs/기술문서/db-guide.md`).

| 엔드포인트 | 변경 | 하위호환 |

| `POST /api/v1/orders` | 서버가 `cycle_start` 를 부여해 부분 유니크 제약을 받음 → 같은 사이클 재확정 시 **409 `ORDER_ALREADY_CONFIRMED`**. **확정 즉시 냉장고 등록 동작 제거** → `delivery_eta` 시점 등록 | ⚠ 신규 409, 부작용 시점 변경 |
| `POST /api/v1/mealplans` | **201 동기 → 202 비동기** 접수 후 `GET /mealplans/{id}` 폴링 (`status=processing → ready/over_budget/failed`) | ⚠ 응답 코드·본문 변경 |

| `GET/PUT/POST /api/v1/cycle*` | `CycleState` 에 `currentOrder` + `mealPlan.mealCount/completedMealCount` 추가 (v1.9) | 추가만 ✅ |

## 🔒 보안
- **GET 부작용 제거 (CWE-650 / CWE-352)**: `GET /orders/preview?refresh=true` 가 저장 초안을 갱신하는 GET 이었고 Origin 검증 미들웨어가 `POST/PUT/PATCH/DELETE` 에만 걸려 CSRF 이중 방어를 우회했다. `POST /orders/{id}/recalculate` 로 메서드를 옮기고 `refresh` 를 제거 (security-design 5-7, QA H-13 "저장 초안 불변" · H-08 "Origin 불일치 403" PASS). "GET/HEAD 핸들러는 값을 바꾸지 않는다" 일반 규칙 신설
- **자동확정 예산 락 게이트 (US-804)**: 자동확정 직전 서버가 식단·재고·시세로 스냅샷을 **1회 재계산**하고 그 금액으로 미매칭(④)·예산 락(⑤) 게이트를 판정. 락 사용자가 한도를 넘겨 자동확정되는 경로 0건(QA S3-07, R-01~R-03)
- **멱등 4중 (FR-816)**: 사용자당 사이클 1회 생성(`last_generated_cycle_start`) · 열린 초안 1건(`uq_orders_open_cycle`) · 확정 1건(`uq_orders_confirmed_cycle`, TOCTOU 최종 방어선) · 냉장고 등록 1회(`inbound_at` compare-and-set). 5세션 동시 inbound → 1회 (S2-01)
- **상태 머신 강제 (CWE-841)**: `order.service._ALLOWED_TRANSITIONS` — `confirmed→draft` 역행·inbound 주문 재확정·`failed→*` 전이는 409 `ORDER_INVALID_STATE`
- **스케줄러도 본인 스코프 (CWE-639)**: due 스캔이 고른 행의 `user_id` 로 모든 후속 조회·변경을 재스코프. 전역 세션 없음
- **입력 검증**: `received` 를 `StrictBool` 로(`"yes"`/`1` 등 422, BUG-009), `timezone` IANA 화이트리스트, `excludeNames` ≤40개·각 ≤200자, `extra='forbid'`
- **정보 노출 제거**: preview `notes` 의 `.env` 변수명 안내 → 사유 코드 `PRICE_LOOKUP_UNAVAILABLE` (BUG-008, CWE-209)
- **푸시**: 본문에 금액·예산·가구 구성 없음(CWE-359), `data.path` 는 `/orders`·`/fridge`·`/mealplan/{id}` 화이트리스트(CWE-601), `notification_logs` 는 `template_key` 만
- **앱 로그인**: OAuth `state` 에 `client(web|app)` 서명 포함, 원타임 코드는 SHA-256 해시만 저장·60초 만료·단일 사용 (`app_login_codes`)
- **정직 표시**: `simulation=true` 고정, `paid/charged` 상태 없음, 가짜 영수증 없음 (US-814)
- 보안 테스트 26건: **24 PASS / 주의 2**(Low — 리미터 공유 버킷 BUG-007, D-1 재계산 재시도 BUG-012) / FAIL 0 (`docs/테스트/보안테스트.md`)

## ✨ 신규 기능

### 자동주문 P0 — 시뮬레이션 확정 (US-701~710, 설계 v1.6)
- `GET /orders/preview`: 최신 식단의 **미완료 끼니** 재료 합 − 냉장고 재고 → `needed`/`covered` 라인 + 네이버 쇼핑(컬리) 추정가. US 는 네이버 미호출·가짜 USD 금지(총액 `0.00 USD`)
- `POST /orders {store}`: 서버 재계산으로 확정 스냅샷(`orders`+`order_items`) 저장. `simulation=true` 고정
- `GET /orders/latest`: 최근 주문 스냅샷 재조회
- 회원 홈 `AutoOrderCard` 활성화(미연동 → 설정 CTA / 연동 → 추천 칩 + "장바구니 보기") + `/orders` 리뷰 화면(살 재료 vs 냉장고 충당, 시뮬레이션 고지). `/orders` 는 보호 라우트(미인증 → `/login?next=/orders`)

### 앱 웹뷰·푸시 알림 (US-001~009 of `앱-웹뷰-푸시알림` 기획, 설계 v1.5 계열)
- `mobile/` Expo(~52) + `react-native-webview` 쉘 신규. 웹↔앱 브리지(`frontend/src/shared/bridge/`, `{v:1, type, payload}`, `BRIDGE_READY`/`PERMISSION_STATUS`/`PUSH_TOKEN`), 앱 감지 = UA `JaringobeApp/` + `window.ReactNativeWebView`
- `notification` 도메인: `PUT/DELETE /notifications/devices` (Expo 토큰 upsert/해제), `GET/PUT /notifications/settings` (끼니 리마인더 3종 + `mealplan_done` + `weekly_nudge`), 리마인더 스케줄러(lifespan asyncio, 30초, `ix_notification_settings_due`)
- 앱 로그인: `GET /auth/{provider}/authorize?client=app` → 콜백이 원타임 코드를 `{APP_SCHEME}://auth?code=` 딥링크로 → `GET /auth/app/session?code=` 가 웹뷰 쿠키로 교환
- `POST /mealplans` 202 비동기 + `mealplan_done`/`mealplanFailed` 푸시, `processing` 좀비는 `MEALPLAN_GENERATION_TIMEOUT_MINUTES`(10분) 후 `failed` 수렴
- 프론트 `/settings/notifications` 페이지, `PushSoftAskSheet`(1회 노출), 로그인 전 수신한 토큰은 로그인 완료 시 지연 등록

### 주간 자동 사이클 — 선순환 루프 완결 (US-801~816 / FR-801~825, 설계 v1.8~v1.10)
```
D-5 활성 사용자 식단 자동 생성 → D-2 주문 초안 + 승인 요청 푸시 → D-1 그레이스 자동확정(5중 게이트)
  → delivery_eta 시점 냉장고 자동 등록 + 보정 푸시 → 식사 완료 시 자동 차감
  → 냉장고 잔여·임박 재료가 다음 식단 프롬프트에 되먹임 → 잔여분만큼 다음 주문 감산 → (월 예산 한도 누적)
```
- **신규 `cycle` 도메인** (`backend/app/domains/cycle/`): `GET /cycle`(상태·`stage` 13종·`weeklyLimit`), `PUT /cycle/settings`(주 1회/2회·기준 요일·타임존·자동확정 on/off·일시정지), `POST /cycle/skip`(이번 사이클 1회 건너뛰기). 설정 행은 최초 호출 또는 온보딩 완료(`PUT /households/me`·예산안 저장) 시 lazy 생성
- **스케줄러**: `run_cycle_loop`(60초) 한 tick = 독립 3스캔(사용자 단계 / 그레이스 자동확정 / 배송→냉장고 등록), 전부 partial index 커버 + `FOR UPDATE SKIP LOCKED`
- **활성 판정 (FR-802)**: 지난 사이클 식사 완료 ≥1 AND `users.last_seen_at` 14일 이내. 탈락 시 `skipped_dormant` + `cycle_paused` 푸시 1회, 홈 복귀 카드 1회(US-811). 신규 사용자는 자동 대상이 아님(첫 식단은 홈 CTA)
- **비용 상한 (FR-817)**: 사용자당 사이클 1회 + 전체 일일 200건(`deferred_quota`, 실패 아님)
- **냉장고 → 식단 되먹임 (FR-805/806)**: 프롬프트에 `Fridge inventory` + `Use these FIRST (expiring soon)` 섹션(KR 3일 / US 5일, 최대 15+25줄). "냉장고에 있다고 수량을 줄이지 마라" 규칙으로 서버 감산과의 이중 감산 방지. 모든 생성 경로(수동·재생성·월간)에 적용, mock LLM 에서는 미적용(알려진 한계)
- **주문 상태 머신**: `draft → awaiting_user → confirmed → cancelled` / `draft|awaiting_user → expired` / `failed` 는 예약 상태(생산 경로 없음). `POST /orders/{id}/approve`(1탭 승인, `excludeNames` 제외), `/cancel`(7일 창, 등록분 롤백 — 소비분은 되돌리지 않음), `/delivery {received}`(받았어요 → 즉시 등록 / 아직 → 롤백 + eta 응답시각+1일, 3회 → `unknown`), `/recalculate`
- **자동확정 5중 게이트** (`awaiting_user` 사유 코드): `AUTO_CONFIRM_OFF` · `US_NO_PRICE` · `STORE_DISCONNECTED` · `UNMATCHED_RATIO`(>30%) · `BUDGET_EXCEEDED`(락 사용자) · `MEALPLAN_OVER_BUDGET`. 차단 시 재알림 1회, 재판정 반복 없음
