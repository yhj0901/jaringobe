## 발견 사항

### EXP-001 — Medium [UI] 공통 로고 `/icon.png`가 HTTP 500

- 재현: `/ko`, `/en`, 각 로그인 화면 및 위저드 첫 단계 방문.
- 기대: 브랜드 이미지가 정상 표시된다.
- 실제: 깨진 이미지 아이콘과 잘린 `Jaringobe` 대체 텍스트가 보인다. DOM의 `img.complete=true`, `naturalWidth=0`.
- 근거: CDP `Network.responseReceived`에 `http://localhost:3000/icon.png`, `status:500`, `mimeType:text/html`; `Log.entryAdded`에 `Failed to load resource: the server responded with a status of 500 (Internal Server Error)` 기록. Resource Timing `responseStatus:500`도 확인.
- 영향: 첫 화면/가입 화면/위저드의 브랜드 영역 품질 저하. 프론트 이미지 요청이므로 `[UI]`로 배정하며, 백엔드 API 500으로 집계하지 않는다. 원인은 코드/서버 로그 분석 없이 단정하지 않는다.

### EXP-002 — Medium [UI] 영문 Breakfast 라벨과 메뉴명이 겹침

- 재현: `/en`의 이번 주 식단 아침 행 확인. 모바일 390×844 및 데스크톱 1200×805에서 재현.
- 기대: Breakfast와 메뉴명이 충분한 간격을 두고 읽힌다.
- 실제: `Breakfast` 오른쪽 글자가 `Oatmeal with berries`, `Bacon and eggs with toast`, `Egg white scramble`의 첫 글자와 겹친다. 한글 `아침` 행에서는 관찰하지 못했다.
- 근거: 초기 영문 모바일 홈, 예산 적용 모바일 홈, 영문 데스크톱 홈 스크린샷에서 겹침을 육안 확인.
- 영향: i18n 키 자체는 번역됐지만 실제 화면에서 끼니와 메뉴를 읽기 어렵다. 메뉴 카드 클릭은 가능하다.

### EXP-003 — Medium [UI] 적용한 월 예산보다 남은 예산 샘플이 큼

- 재현 A: en → 예산 작성 → 1인, 월 $120, Salad & Vegan, Diet-focused → Build my plan.
- 실제 A: 저장 초안 `amount:"120", currency:"USD"`인데 홈 `Remaining $132.00`, `Saved $41.00`, `Waste prevented $12.00`. 재진입해도 동일.
- 재현 B: ko → 1인, 월 ₩130,000, 한식, 건강 → 완료.
- 실제 B: 저장 초안 `amount:"130000", currency:"KRW"`인데 홈 `남은 예산 ₩132,000`.
- 기대: 내 예산안을 반영했다고 설명하는 남은 예산은 월 총예산과 양립해야 한다. 정적 샘플이라도 총예산을 넘는 잔액은 피하거나 샘플의 기준을 명확히 설명해야 한다.
- 영향: US-104의 예산 반영 체험과 예산 락 설명에 대한 신뢰 저하. 실제 지출/주문 초과를 발견한 것은 아니므로 회원 결제 결함으로 확대하지 않는다.

### EXP-004 — Low [UI] 레시피 내용이 메뉴와 무관한 공통 자리채움 문구

- 재현: ko/en의 여러 끼니 카드로 레시피 열기.
- 실제: 현미밥과 달걀국, 그릭요거트와 견과, 두부면 야채볶음, Cheeseburger, Baked salmon 모두 20분/쉬움과 같은 조리 3문장. ko는 “재료를 깨끗이 씻고 알맞게 손질해 준비해요”, “재료를 넣고 알맞게 조리하며 간을 맞춰요”, “그릇에 보기 좋게 담아 맛있게 즐겨요”; en도 같은 의미의 공통 문구다.
- 기대: 샘플 레시피임을 시트에서도 분명히 알리거나 메뉴별로 재료·순서가 다른 최소한의 조리 예시를 제공한다.
- 영향: 시트가 열리고 내용은 채워져 있지만 실제 조리법으로 활용할 정보가 부족하다. 시트의 `AI 추천 레시피`/`AI recipe` 배지에 비해 내용이 빈약하다. 게스트 정적 샘플 및 제공된 AI mock 조건 자체를 결함으로 집계한 것은 아니다.

## 기획 정합성 확인 필요 — 확정 결함 건수 제외

구 게스트홈 FR-104는 로캘별 월 예산 프리셋+직접입력을 요구하지만 실제 게스트 위저드는 구성원·나이, 예산 슬라이더·락, 선호음식·식단 방향의 신규 온보딩형 UI다. 실제 en 1인 슬라이더 범위는 $60~170, ko 1인은 ₩80,000~220,000으로, 구 문서의 $300/₩300,000 프리셋을 선택하는 UI가 없다.

후속 `진입순서-가입온보딩.md`는 회원 온보딩에 이런 슬라이더 UI를 명시한다. 게스트까지 의도적으로 통합한 것인지, 구 FR-104를 유지해야 하는지 임의 판단하지 않고 코디네이터에 질문했다. 질문 ID는 `msg_6df206720d0e`; 답변에 따라 문서 갱신 또는 `[설계]` 후속 조치를 결정해야 한다.

## 콘솔·네트워크 검증과 한계

- 각 주요 탐색에서 `drainEvents()`를 사용하고 CDP `Network.enable`, `Runtime.enable`, `Log.enable` 후 네트워크 응답/실패, 예외, 콘솔 오류를 확인했다. CLI 세션별 재연결 때문에 전체 방문의 모든 요청을 하나의 연속 HAR로 저장한 것은 아니다.
- `window`의 error/unhandledrejection 리스너도 마지막 확인에 설치했으며 수집 배열은 비어 있었다. 초기 탐색 전체를 리스너가 덮었다고 주장하지 않는다.
- 실제 확인 오류는 EXP-001의 이미지 500. 같은 요청의 Network/Log/Resource Timing 기록을 중복 결함으로 세지 않았다.
- `apple-mobile-web-app-capable` 메타 사용 중단 경고와 React DevTools 개발 안내가 있었다. 이것만으로 제품 기능 결함을 추가 집계하지 않았다.
- 관찰한 예산 완료 구간에서는 게스트 입력을 전송하는 API 요청이 발견되지 않았다. 서버 차원의 전체 요청 감사나 전송 부재의 보안 증명은 아니다.
- 브라우저 헬퍼에서 보이지 않는 버튼 클릭/부정확한 영어 locator에 따른 `ElementResolutionError`가 일부 발생했다. 실제 스크롤과 최신 화면 기준 locator로 재시도해 진행했으며 제품의 JavaScript 오류와 구분했다. `ESC` 별칭 대신 정확한 `Escape`로 닫기를 재검증했다.

## 코디네이터 검증 (2026-09-05)

보고 내용을 직접 재현해 확인했다.

### 확인된 것

**로고 이미지 500 — 사실.** 실측:
```
GET /icon.png        → 500
GET /apple-icon.png  → 500
GET /ko/icon.png     → 200
```
브라우저에서도 `img.naturalWidth === 0` 으로 깨져 있음을 확인했다. 로캘 프리픽스가 없는 루트 경로에서만 실패한다.

**월 예산보다 큰 잔액 — 사실. 근본 원인까지 확인했다.**
- 샘플 매트릭스의 예산 밴드는 프리셋 `300/500/700/1000`(`shared/config/constants.ts` `BUDGET_PRESETS`)을 기준으로 만들어졌다.
- `toBudgetBand` 는 최저 프리셋보다 낮은 금액을 전부 `p1` 로 접는다.
- `p1` 의 1인 `remaining` 은 en `132` / ko `132000` 이다.
- 그런데 통일된 온보딩 위저드는 프리셋보다 훨씬 낮은 금액(en 1인 60~170)을 허용한다.
  → 예산 `$120` 입력 시 "남은 예산 `$132`" 가 나온다.

즉 **위저드의 입력 범위가 샘플 매트릭스가 전제한 범위를 벗어나** 생긴 구멍이다.
게스트 홈은 전환 장치인데 첫 화면에서 앞뒤가 안 맞는 숫자를 보여주므로,
`예시`/`체험 모드` 라벨이 있어도 신뢰를 깎는다.
