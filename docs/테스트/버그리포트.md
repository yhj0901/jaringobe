## High

### BUG-001 [API]/[설계] 자동확정 예산 락 게이트가 초안 금액으로 판정된 뒤 재계산 금액이 한도를 넘어도 확정된다 — **High**

- **재현**: 월예산 400,000 KRW `locked=true`. D-2 초안 추정가 80,500(시세 ×1). D-1 자동확정 시점에 시세가 ×4(322,000)로 바뀐 상태에서 스캔 ②를 실행 → 한도 253,333.33.
- **기대**: 게이트 ⑤ `estimatedTotal ≤ cycle_limit` 가 **확정될 금액** 기준으로 판정되어 `awaiting_user/BUDGET_EXCEEDED`.
- **실제**: `auto_confirm_order` 가 `order.estimated_total`(초안 스냅샷 80,500)으로 통과시킨 뒤 `_confirm_existing` 이 `_build_preview` 로 재계산한 322,000 을 저장하며 `confirmed, auto_confirmed=true`. (S3-07)
- **위치**: `backend/app/domains/order/service.py` `auto_confirm_order`(한도 비교) → `_confirm_existing`(재계산·저장, 한도 재검증 없음). 미매칭 비율 게이트 ④도 같은 구조(초안 라인 기준).
- **왜 High**: 예산 락은 "자동화가 넘을 수 없는 선"(security-design 5-6)이고 US-804 의 핵심 약속이다. 재계산 트레이드오프(api-spec 10-1)는 명시돼 있지만 그 결과가 게이트를 우회하면 안 된다. 시뮬레이션이라 금전 손실은 없으나 실결제 전환 시 그대로 사고가 된다.
- **설계 정합**: architecture 3-9-5 도 "⑤ 통과 → 서버 재계산 → confirmed" 순서로 적혀 있어 설계 자체가 이 구멍을 갖고 있다. **[설계] 3-9-5 정정 필요** — 재계산 후 한도(및 미매칭 비율)를 다시 검증하고 초과 시 `awaiting_user` 로 전이.
- **회귀**: 하네스 S3-07 (초안 ≤ 한도, 재계산 > 한도 → awaiting_user 기대).

### BUG-002 [API] 초안 생성 실패 핸들러가 `MissingGreenlet` 로 죽어 백오프·폴백이 동작하지 않고 매 tick 네이버를 재호출한다 — **High**

- **재현**: D-2 스캔에서 `store_service.build_cart` 가 예외(네이버 장애). `_process_draft_stage` 의 `except` 블록이 `await db.rollback()` 후 `settings.id` 에 접근.
- **기대**(기획 5-4, architecture 3-9-3): `stage_attempts` 1→2→3, `next_run_at` = now+1/5/15분, 4회째는 `force_unmatched=True` 로 **시세 없이 needed 목록만으로 초안 생성**(전량 `matched=false`) → 미매칭 게이트가 사용자 승인으로 전환. 루프는 멈추지 않는다.
- **실제**: rollback 이 세션의 모든 인스턴스를 만료시켜 `settings.id` 접근이 동기 refresh 를 유발 → `sqlalchemy.exc.MissingGreenlet` 이 핸들러 밖으로 전파 → 스케줄러 외부 `except` 가 롤백·로그만 하고 `stage_attempts`/`next_run_at` 은 그대로. 다음 tick(60초)마다 `create_draft` 전체(네이버 5페이지 × needed 품목 수)를 즉시 재시도. 30 tick 동안 네이버 30회 호출, 초안 0건, 폴백 미발생. (S6-01/02/04) 장애가 D-1 을 넘기면 그 주 초안·승인이 없고, 다음 D-5 에 새 사이클로 넘어가 조용히 건너뛴다.
- **위치**: `backend/app/domains/cycle/service.py` `_process_draft_stage` — `except Exception: await db.rollback()` 직후 `select(...).where(UserCycleSettings.id == settings.id)`. (수정 힌트: `setting_id = settings.id` 를 try 앞에서 보관하거나 `db.refresh` 대신 새 세션 사용.)
- **테스트 갭**: `tests/test_cycle_scheduler.py::test_fourth_draft_failure_persists_terminal_stage` 는 `create_draft` 를 **DB 접근 전에** raise 하도록 mock 해서 트랜잭션이 시작되지 않아 rollback 이 만료를 일으키지 않는다 → 결함이 가려진다. 회귀 테스트는 `_build_preview` 내부(쿼리 이후)에서 실패시켜야 한다.
- **왜 High**: 기획 5-4 예외 흐름이 통째로 미이행 + 자기 유발 자원 소모(CWE-770, 외부 API 쿼터 소진 위험) + 사용자에게 "장바구니를 만들지 못했어요" 류 어떤 신호도 가지 않는다.
- **회귀**: 하네스 S6-01/02/04.

## Medium

### BUG-003 [API] 확정 주문이 이미 있는 사이클에 스케줄러가 새 초안을 만들어 `stage` 가 `drafted` 로 덮이고 불필요한 승인 알림이 나간다 — **Medium**

- **재현 A**: D-2 이전에 사용자가 `POST /orders` 로 명시 확정 → D-2 스캔 ① 이 `create_draft` 실행 → 같은 `cycle_start` 에 `confirmed` + `draft` 공존. `GET /cycle` stage=`drafted`, `GET /orders/latest` 는 새 초안, `order_approval` 푸시 발송. 승인을 누르면 409 `ORDER_ALREADY_CONFIRMED`. D-1 자동확정은 게이트 ⓪이 초안을 `expired` 처리하므로 이중 확정은 없다(S8-03/04/05).
- **재현 B**: 확정 후 `PUT /cycle/settings {timezone}` → `update_settings` 가 `last_generated_cycle_start == cycle_start` 이면 `next_run_at = draft_at(...)`(이미 지난 D-2)로 되돌려 다음 tick 에 재현 A 와 같은 초안 생성 (S8-08/09).
- **기대**: `create_draft` 는 사이클에 `confirmed` 가 있으면 초안을 만들지 않고 `last_stage` 만 전진; `update_settings` 는 `last_stage` 가 `drafted` 이상이면 다음 사이클 D-5 로 재계산.
- **위치**: `order/service.py` `create_draft`(`_existing_confirmed` 미확인), `cycle/service.py` `update_settings` 재계산 분기, `_derive_stage`(최신 행 우선).
- **회귀**: S8-03/04/08/09.

### BUG-004 [설계]/[API] `cycle_limit` 의 확정액이 `confirmed_at` 의 달로 귀속되어 월초 사이클 확정분이 다음 달 한도에서 빠진다 — **Medium**

- **재현**: 기준 요일 목요일, 사이클 10/1(목). 초안 9/29, 자동확정 9/30(D-1) 80,500. 10/8 사이클 한도 = 400,000×14/31 = 180,645.16 이어야 하는데(10/1 분 차감) 실제 180,645.16 **그대로** — 80,500 이 9월 `committed` 로 잡혀 10월에 차감되지 않는다. 10월 내내 한 사이클분 과대 허용. (S8-07)
- **기대**: 확정액 귀속을 `cycle_start` 가 속한 달(안분과 같은 축)로 통일.
- **위치**: `backend/app/domains/budget/service.py` `cycle_limit` — `Order.confirmed_at ∈ [month_start, accrual_end)`. architecture 3-9-4 수식이 `confirmed_at` 로 적혀 있으므로 **[설계] 정정 대상**.
- **회귀**: S8-06/07.

## Low

### BUG-005 [API] 자동확정 경합 핸들러(`ORDER_ALREADY_CONFIRMED`)가 rollback 후 만료 객체 `order.id` 에 접근해 `MissingGreenlet` — **Low**
- `order/service.py` `auto_confirm_order` `except ApiError` 분기. 실제 경합에서는 다음 tick 게이트 ⓪이 `expired` 처리해 자가 회복하므로 Low. BUG-002 와 같은 결함 유형(rollback 후 속성 접근). (S8-15)

### BUG-006 [API] 저장 초안 `GET /orders/preview` 가 부분 충당분(`fromFridge`)을 잃는다 — **Low**
- 스냅샷 needed 라인에 `from_fridge` 를 저장하지 않아 `_preview_from_order` 가 `needed=toBuy, fromFridge=0` 으로 복원. 계란 실제 need 16·재고 4 → 응답 `needed 12 / fromFridge 0 / toBuy 12`. toBuy·합계는 정확하나 "냉장고가 충당" 표시가 부분 충당을 보여주지 못한다. (S1-08b)

### BUG-007 [API] 액션 리미터가 5개 엔드포인트 공유 버킷 — **Low**
- `core/ratelimit.py` `cycle_action_user_limiter` 하나를 `PUT /cycle/settings`·`POST /cycle/skip`·`approve`·`cancel`·`delivery` 가 공유(합산 5회/분). 스펙(api-spec 9-2/9-3/10-1~10-3)은 각 5회/분. 설정 토글 몇 번 뒤 승인 버튼이 429 를 받을 수 있고, 타인 주문 IDOR 시도(403)도 본인 버킷을 소진한다. 주석은 "10회/분"으로 값(5)과 불일치. (H-20)

### BUG-008 [API] `GET /orders/preview` `notes` 에 서버 내부 설정 안내 노출 — **Low**
- `"네이버 API 키 미설정 — 검색 결과 없음(.env NAVER_CLIENT_ID/SECRET 필요)"` 가 사용자 응답에 내려간다(`order/service.py`, `store/service.py`). 값 노출은 아니지만 운영 문구가 사용자 계약에 섞였다(CWE-209 계열). 사용자용 사유 코드로 대체 권장. (H-48)

### BUG-009 [API] `DeliveryUpdateRequest.received` 가 `"yes"` 등 문자열을 `true` 로 수용 — **Low**
- pydantic lax 변환. 스펙은 boolean 아닌 값 422. `StrictBool` 권장. (H-31)

### BUG-010 [UI] 설정 카드의 타임존이 표시만 되고 변경 UI 가 없다 — **Low**
- ui-design 14-5 "타임존 (표시 + 변경)". `CycleSettingsCard.tsx` 는 `{cycle.timezone}` 텍스트만. 서버 `PUT /cycle/settings {timezone}` 은 동작한다(H-21 검증).

### BUG-011 [인프라]/[API] 앱 로거 미구성으로 사이클 구조화 로그가 출력되지 않는다 — **Low**
- `logging` 설정이 없어 `app.*` 로거의 INFO(`"주간 사이클 스케줄러 시작"`, `_log_transition` 단계 전이·스킵 사유)가 프로세스 출력에 나타나지 않는다(uvicorn 액세스 로그만 보임 — :8012 실측, 컨테이너 `jaringobe-backend` 로그 동일). architecture 3-9-12 관측성 요구 미충족. BUG-002 같은 장애가 로그에 남지 않아 운영에서 알아차릴 수 없다(예외는 `logger.exception` 이라 WARNING 이상으로 보이긴 한다).

## 판정 근거 요약

- 통과 조건 "Critical 0 / High 0" 중 **High 2건 존재** → 불통과.
- High 2건은 모두 [API] 단일 파일 수준 수정 범위(`order/service.py` 게이트 재검증, `cycle/service.py` 핸들러). 수정 후 하네스 S3-07·S6-01/02/04 와 기존 회귀(369+509) 재실행 시 재판정 가능.
- 나머지 Medium 2건은 GATE 조건에 걸리지 않으나, BUG-004 는 [설계] 정정을 동반해야 하므로 설계 에이전트 재소집 권고.
