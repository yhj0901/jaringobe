# 선순환 루프 완결 — 주간 자동 사이클 기획서

## 개요 | 배경 및 목적

자린고비의 3대 축(예산 락 식단 / 가상 냉장고 / 자동 주문)은 **개별 기능으로는 대부분 살아 있으나, 사이클로 연결되어 있지 않다.** 사용자가 매 단계마다 앱에 들어와 버튼을 눌러야 다음 단계가 진행되고, 어느 한 단계라도 건너뛰면 루프가 그 자리에서 멈춘다. 사업계획서가 정의한 선순환은 다음과 같다.

```
① 입력 (가족·예산 락 설정)
  → ② AI 식단 + 자동 주문 (최저가 검색 → 식단 → 자동 결제)
    → ③ 가상 냉장고 (식사 완료 시 자동 차감)
      → ④ 동적 감산 (남은 재료만큼 다음 주 장보기 비용 자동 차감 = 예산 방어)
        ↩ ②로 순환
```

본 기획서는 이 순환을 **주(week) 단위 자동 사이클**로 닫는 것을 목표로 한다. 즉, 사용자가 최초 1회 설정(①)을 마치면 이후에는 **개입하지 않아도 매주 식단이 생성되고 → 주문 초안이 만들어지고 → 승인(또는 그레이스 자동확정) 후 → 배송예정일에 냉장고가 채워지고 → 식사 완료로 차감되고 → 잔여분이 다음 주 식단·주문에 반영**되어야 한다. 사용자의 역할은 "진행시키는 사람"이 아니라 "필요할 때 되돌리는 사람"으로 바뀐다.

**본 기획서가 새로 만드는 것은 기능이 아니라 "연결"이다.** 아래 갭 분석이 보여주듯 개별 단계는 대부분 구현되어 있고, 빠진 것은 (1) 시간 축을 도는 스케줄러, (2) 냉장고 → 식단 생성으로의 되먹임, (3) 배송 시점 냉장고 등록, (4) 자동화가 실패할 때의 예외 처리다.

### 이 기획이 전제로 삼는 것

- **origin/main = efc8376** — auth·household·budget·mealplan·fridge·store 6개 도메인, API 25경로 라이브
- **feature/auto-order-p0** (main+4, alembic 0009) — 자동주문 P0(preview/확정/latest + fridge inbound). **본 기획은 이 브랜치 구현을 기정사실로 두고 그 위에 무엇이 더 필요한지를 쓴다.**
- **feature/app-webview-push** (alembic 0008 번호충돌 상태) — 앱 웹뷰 쉘 + notification 도메인(디바이스 토큰·설정·발송·리마인더 스케줄러) + mealplan 비동기 생성 전환

## 범위: In Scope / Out of Scope

### In Scope

1. **주간 사이클 스케줄러** — 사용자별 주기(주 1회/2회)·요일·타임존 기준으로 식단 생성 → 주문 초안 → 자동확정 → 냉장고 등록을 순서대로 트리거
2. **주간 롤링 식단 자동 생성** — 활성 사용자에게 주 1회 다음 주 식단을 미리 생성(조건부 자동, Q6=C). 휴면 사용자는 현행 버튼 방식 유지
3. **냉장고 → 식단 되먹임** — 냉장고 잔여 재고와 유통기한 임박 재료를 식단 생성 입력에 포함 (사업계획서 축2 "임박 재료 우선 배치")
4. **1탭 승인 + 24h 그레이스 자동확정** — 주문 초안을 푸시/인앱으로 알리고, 사용자가 승인하거나 24시간 무응답 시 예산 락 한도 내에서만 자동 확정
5. **배송예정일 기반 냉장고 자동 등록** — 주문에 `delivery_eta` 를 두고 그 시점에 needed 라인을 냉장고에 inbound. 등록 직후 푸시로 사용자 보정 유도
6. **주기 설정 UI** — 주 1회/2회, 기준 요일, 자동확정 on/off, 사이클 일시정지
7. **예외 흐름 전체** — 예산 초과 / 품절·미매칭 / 배송 지연 / 주문 실패 / 생성 실패 / 연동 해제 / 중복 확정 / 휴면 전환
8. **LLM 비용 방어선** — 사용자당 주 1회 생성 상한, 전체 일일 상한, 활성 판정 정책 파라미터화
9. **웹 우선 → iOS/Android 확장 로드맵** — 웹뷰 접근 타당성 평가 및 네이티브 전환 필요 기능 구분

### Out of Scope (이관 / 후속)

- **실결제·KR 마트 계정 자동화** — 마트 약관 위반 리스크와 자격증명 보관 문제가 커서 별도 기획 + 법무 검토가 선행되어야 한다. 루프 완결 자체는 시뮬레이션 확정(`simulation=true`)으로 증명 가능하므로 이번 사이클 범위 밖. 로드맵 단계로만 기술 (Q4 결정)
- **US Walmart / Instacart 공식 API 실연동** — 파트너 키 전제. US 는 needed 목록까지만, 가짜 USD 시세 금지 (auto-order-p0 FR-703 유지)
- **대체 재료 자동 제안** (품절 시) — P2
- **주문 취소·환불·배송 추적 실연동** — 스토어 실연동 이후
- **광고성 푸시** — 정보통신망법상 별도 명시 동의 + 야간 전송 제한 체계 선행 필요 (app-webview-push 기획 결정 승계)
- **멀티 인스턴스 스케줄러 분산 락** — 현재 단일 인스턴스 전제. 확장 시 설계 재소집
- 앱 스토어 제출 실무(계정·심사 대응) — app-webview-push 기획 소관

### 1-5. `POST /mealplans/monthly` 처리 방침 (Q2 결정)

제품 정본 사이클은 **주간 롤링**으로 확정되었다. 현재 코드에 공존하는 `POST /mealplans/monthly`(`mealplan/service.py:434 build_monthly_plan`)는 다음과 같이 정리한다.

| 방침 | 내용 |
|------|------|
| **유지하되 제품 정본에서 제외** | 엔드포인트를 삭제하지 않는다. 이유: `_prorate()`(월 예산을 "오늘 포함 남은 일수" 비율로 안분)는 **주간 사이클이 월 예산 한도를 나눠 쓸 때 그대로 필요한 계산**이다 |
| **역할 축소** | "월 식단 일괄 생성 + 첫 주기 주문"이라는 **제품 흐름으로서의 용도는 폐기**한다. 회원 UI 는 이 엔드포인트를 호출하지 않는다 (현재도 호출하지 않음) |
| **재배치 (설계 이관)** | `_prorate` 로직을 주간 사이클의 **주간 예산 한도 산출기**로 승격 — "이번 주에 쓸 수 있는 금액 = 월 예산 × (이번 주 일수 / 그 달 일수) − 이번 달 기확정 금액". 엔드포인트로 남길지 내부 함수로 내릴지는 설계 단계에서 확정 |
| **문서 표기** | api-spec 에 "내부/실험용 — 제품 흐름 비사용" 으로 명시 |

| **FR-812** | **예산 락 게이트**: 자동확정 직전, `추정 합계 + 이번 달 기확정 금액 ≤ 월 예산` 을 검증한다. 월 예산 대비 이번 주 한도는 `_prorate` 안분 결과를 쓴다(1-5 참조). **초과하면 자동확정을 중단**하고 "예산을 넘을 것 같아요" 알림 + 사용자 승인 요구. 예산 락이 해제된(`locked=false`) 사용자는 경고 배너만 띄우고 자동확정을 허용한다 | P0 |
| **FR-813** | **미매칭 게이트**: needed 라인 중 `matched=false` 비율이 임계(초기값 30%, 정책 파라미터)를 넘으면 자동확정을 중단하고 사용자 확인을 요구한다. US(시세 어댑터 없음)는 이 게이트를 적용하지 않고 **항상 사용자 승인**을 요구한다 — 추정가가 0 이라 자동확정의 근거가 없기 때문 | P0 |
| **FR-814** | **주기 설정**: 주 1회 / 주 2회, 기준 요일, 자동확정 on/off, 사이클 활성/일시정지를 사용자가 설정한다. `orders.frequency` CHECK 를 `('weekly','biweekly')` 로 확장(GATE 3). **KR 기본 = 주 1회, US 기본 = 주 1회 고정 권장**(대량 배송 전략) | P0 |
| **FR-815** | **취소·되돌리기**: 확정 후 냉장고 등록 전까지는 `POST /orders/{id}/cancel` 로 취소할 수 있다(`status='cancelled'`). 이미 냉장고에 등록됐다면 **해당 주문으로 등록된 항목만** 롤백한다 — `order_items` 스냅샷 기준으로 삭제하며, 사용자가 이미 소비(차감)한 분은 되돌리지 않는다(음수 재고 금지). 실결제 도입 후에는 스토어 취소 마감 시각까지만 허용 | P0 |
| **FR-816** | **멱등 (자동화 전제 조건)**: `orders` 에 `cycle_start date` 를 두고 `UNIQUE(user_id, cycle_start, status='confirmed')` 성격의 제약(부분 유니크 인덱스)으로 **같은 사이클 이중 확정을 DB 레벨에서 차단**한다. auto-order-p0 가 P1 로 이관했던 항목을 **자동화 도입과 함께 P0 로 승격한다** — 사람이 두 번 누르는 것은 실수지만 스케줄러가 두 번 도는 것은 냉장고 인플레를 낳는 재해다 | P0 |
| **FR-822** | **정직 표시 유지**: `simulation=true` 고정, `paid`/`charged` 상태 도입 금지, 가짜 승인번호·영수증 금지. 자동확정 알림·화면에도 "연동 표시 기준 시뮬레이션 (실결제 아님)" / EN 동등 문구를 유지한다 (auto-order-p0 결정 승계, US-814) | P0 |

## 4. 주간 사이클의 시간 축

### 4-1. 기준

- 모든 시각은 **사용자 타임존 로컬 시각** 기준으로 판정하고, 저장·스캔은 **UTC**(`next_run_at`)로 한다 (DST 대응 — 로컬 시각 + IANA 타임존 쌍 저장, app-webview-push 의 `notification_settings` 패턴 승계)
- 아래 요일·시각은 **초기 기본값**이며 사용자가 기준 요일을 바꾸면 통째로 시프트된다. 예시는 "일요일 배송 도착"을 기준 요일로 잡은 경우다
- 사이클 길이 = 주 1회(7일) 또는 주 2회(3~4일) — 주 2회는 같은 시간 축을 절반 주기로 반복한다

### 4-2. 표준 사이클 (주 1회, 기준 요일 = 일요일 도착)

| 시점 | 로컬 시각 | 일어나는 일 | 사용자 개입 | 되돌릴 수 있는가 |
|------|-----------|-------------|-------------|------------------|

### 4-3. 자동확정 게이트 (D-1 판정)

```
[초안 status='draft'] + 24h 경과
   ├─ ① 예산 락 잔여 한도 이내?          아니오 → awaiting_user + "예산을 넘을 것 같아요"
   ├─ ② 미매칭 비율 ≤ 임계(30%)?          아니오 → awaiting_user + "못 찾은 재료가 많아요"
   ├─ ②' 국가 = US?                        예    → awaiting_user (추정가 없음 — 자동확정 근거 부재)
   ├─ ③ 대상 스토어 connected?             아니오 → awaiting_user + 설정 CTA
   ├─ ④ 이 사이클에 확정 주문 없음?        아니오 → 스킵 (멱등, 아무 일도 하지 않음)
   ├─ ⑤ 자동확정 설정 on?                  아니오 → awaiting_user
   └─ 전부 통과 → status='confirmed' (서버 재계산 스냅샷) → delivery_eta 설정
```

- `awaiting_user` 는 **주문을 만들지 않는다**. 초안을 남기고 사용자를 기다린다. 재알림은 사이클당 최대 1회 추가(알림 피로 방지)
- 사이클 종료(다음 D-5)까지 승인되지 않은 초안은 `expired` 처리하고 다음 사이클 초안으로 대체한다 — 오래된 초안이 뒤늦게 확정되어 유효하지 않은 식단의 재료를 사는 일을 막는다

### 4-4. 사용자 개입 지점 요약 (5개)

| # | 개입 지점 | 성격 | 안 해도 루프가 도는가 |
|---|-----------|------|----------------------|
| 1 | 설정 변경(가구·예산·선호·주기) | 최초 1회 필수, 이후 선택 | ✅ (최초 설정 이후) |
| 2 | 식단 재생성 | 선택 | ✅ |
| 3 | 주문 초안 승인·편집·건너뛰기 | 선택 (24h 후 자동확정) | ✅ |
| 4 | 냉장고 등록 보정 | 선택 (권장) | ✅ — 단 보정하지 않으면 감산 정확도가 떨어진다 |
| 5 | **식사 완료 체크** | **사실상 필수** | ❌ — **루프의 유일한 필수 입력** |

> **핵심 설계 판단**: 식사 완료 체크만이 시스템이 알 수 없는 정보(실제로 그 끼니를 해 먹었는가)다. 나머지 4개는 전부 자동화 가능하며, 실제로 자동화한다. 따라서 Zero-UX 의 실질적 정의는 **"주 N회 체크 외에 아무것도 하지 않아도 되는 상태"** 이고, 끼니 리마인더 푸시가 이 유일한 입력의 수행률을 방어하는 장치다. 완료 체크가 없으면 냉장고가 실제보다 가득 차 있다고 판단해 다음 주문이 과소 발주되므로, **완료율이 낮은 사용자는 활성 판정(FR-802)에서 자연히 탈락해 자동 사이클이 멈춘다** — 이는 버그가 아니라 안전장치다.

## 5. 예외 흐름

### 5-1. 예산 초과

| 상황 | 처리 |
|------|------|
| **식단이 예산 초과로 생성됨** (`status='over_budget'`) | 이미 구현된 재시도 루프(`_generate_within_budget`, 최대 재시도 후 **임의로 자르지 않음**)를 그대로 따른다. 자동 사이클에서는 **자동확정을 금지**하고 `awaiting_user` 로 두며, "예산을 넘는 식단이에요 — 다시 만들까요?" 알림 + 재생성 CTA |
| **주문 추정가가 주간 예산 한도를 초과** | FR-812 게이트에서 자동확정 중단. 사용자에게 초과액과 함께 제시하고 ① 승인(락 해제 상태만) ② 품목 제외 후 승인 ③ 식단 재생성 3가지 경로 제공 |
| **예산 락이 해제된 사용자**(`locked=false`) | 경고 배너만 표시하고 자동확정 허용. 락은 사용자가 명시적으로 건 장치이므로 해제 상태에서 시스템이 대신 막지 않는다 |
| **월 중 예산 소진** | 남은 사이클은 초안까지만 만들고 자동확정하지 않는다. "이번 달 예산을 다 썼어요" 알림 1회 |

### 5-2. 품절 · 재료 미매칭

| 상황 | 처리 |
|------|------|
| **일부 재료 미매칭** (`matched=false`) | 확정 자체는 허용. 해당 라인은 `unit_price=null` 로 스냅샷하고 추정 합계에서 제외. 리뷰 화면에 "시세 없음" 표기 |
| **미매칭 비율 > 임계(30%)** | FR-813 — 자동확정 중단, 사용자 확인 요구 |
| **US (시세 어댑터 없음)** | 항상 사용자 승인. 가짜 USD 가격 생성 절대 금지 (auto-order-p0 결정 승계) |
| **네이버 API 키 미설정 / LLM 미설정** | 기존 동작 유지 — `matched=false`, `total=0`, note 표기. 사이클은 계속 돌되 자동확정은 미매칭 게이트에 걸려 사용자 승인으로 전환 |
| **대체 재료 제안** | **P2 — 본 기획 범위 밖.** 임의 대체는 알레르기 위험(생성 시 검증한 알레르기 제약이 대체 재료에는 적용되지 않음)이 있어 별도 기획 필요 |

### 5-3. 배송 지연 · 미도착

| 상황 | 처리 |
|------|------|
| **`delivery_eta` 도달** (정상) | FR-820 자동 등록 + 보정 알림 |
| **실배송 신호 없음** (시뮬레이션 단계의 기본 상황) | `delivery_eta` 는 추정치이므로, 등록 알림 문구를 **"담았어요"가 아니라 "받으셨나요? 냉장고에 담아둘게요 — 아직이면 알려주세요"** 로 하고 사용자가 "아직 안 왔어요"를 누르면 등록을 롤백하고 `delivery_eta` 를 +1일 미룬다 |
| **3회(3일) 연속 "아직"** | 자동 등록을 중단하고 주문을 `delivery_unknown` 으로 표시. 사용자가 직접 "받았어요"를 누를 때만 등록. 다음 사이클 초안은 **이 주문이 냉장고에 없다는 전제**로 계산되어야 한다(과소 발주 방지) |
| **실연동 도입 후** | 스토어 배송 상태 웹훅으로 대체. 본 기획의 추정 로직은 폴백으로 남김 |

### 5-4. 주문 실패

| 상황 | 처리 |
|------|------|
| **초안 생성 실패** (네이버/LLM 호출 실패, 타임아웃) | 지수 백오프 재시도 3회(1분/5분/15분). 최종 실패 시 **시세 없이 needed 목록만으로 초안 생성**(`matched=false` 전량) — 루프를 멈추지 않는다. note 에 사유 기록 |
| **429 rate limited** | 재시도 대상. 스케줄러는 사용자별로 분산 실행(같은 분에 몰리지 않게 지터 적용)해 자기 자신이 한도를 치지 않게 한다 |
| **확정 트랜잭션 실패** | 주문·라인 저장과 fridge inbound 는 **분리된 시점**(확정 vs `delivery_eta`)이므로 확정 트랜잭션은 주문+라인만 원자적으로 처리하면 된다. 실패 시 `status='failed'` + 알림 "장바구니를 만들지 못했어요" + 수동 진입 CTA. **냉장고는 건드리지 않는다** |
| **inbound 실패** | `inbound_at` 미기록 → 다음 스캔에서 재시도. 부분 등록 방지를 위해 라인 전체를 한 트랜잭션으로 처리 |

### 5-5. 식단 생성 실패

| 상황 | 처리 |
|------|------|
| **`status='failed'`** | 다음 날 09:00 에 **1회만** 재시도. 재실패 시 포기하고 "다음 주 식단을 만들지 못했어요" 알림 + 수동 생성 CTA. **지난 주 식단을 그대로 연장하지 않는다** (오래된 식단으로 잘못된 주문이 나가는 것을 막기 위해) |
| **`processing` 영구 잔류** (서버 재시작 등) | app-webview-push 의 `_is_stale_processing` 회수 로직이 타임아웃 초과분을 `failed` 로 수렴시킨다 — 그대로 승계 |
| **식단이 없는 상태로 D-2 도달** | 초안을 만들지 않는다(`MEALPLAN_NOT_FOUND`). 사이클을 조용히 건너뛰고 다음 사이클로 넘어간다. 알림은 5-5 첫 행에서 이미 나갔으므로 중복 발송하지 않는다 |

### 5-6. 기타

| 상황 | 처리 |
|------|------|
| **스토어 연동 해제** | 자동확정 게이트 ③ 에서 중단. "스토어 연동이 풀렸어요" 알림 **주 1회 한도**. 초안 생성(preview)은 연동 없이도 계속 동작한다 |

### 자동화 특유의 보안 판단

> **"자동으로 돈을 쓰는 시스템"의 신뢰 경계**: 현재는 `simulation=true` 이므로 자동확정이 실제 금전 손실을 만들지 않는다. 그러나 **실결제 도입 시점에 자동확정 로직을 그대로 켜두면 안 된다.** 실결제 전환은 ① 자동확정에 대한 **별도 명시 동의**(약관 + 앱 내 재확인) ② 1회 상한액 설정 ③ 확정 전 N시간 취소 가능 기간 보장 ④ 결제 실패 시 재시도 정책을 **선행 조건**으로 하며, 이는 실결제 기획의 GATE 항목으로 이관한다.

- 기존 `ix_orders_user_created` 유지

### 9-3. 변경 — `fridge_items` (마이그레이션 불필요)

- `source` 는 varchar(20) 이며 **DB CHECK 가 없다**. Pydantic Literal 에 값만 정리한다: 현재 `manual|delivery|mealplan` + auto-order-p0 가 추가한 `order`. **`delivery` 와 `order` 의 정리(통합/병존)는 설계 확정 사항** — 본 기획은 "배송 시점 등록"을 `delivery` 로 보는 것이 의미상 맞다고 권고한다
- inbound 는 기존 `add_items` 처럼 **새 행 추가**(병합 없음). 유통기한은 `null`(사용자 입력 전까지 추정 금지)

### 9-4. 변경 — `notification_settings` (app-webview-push 테이블에 값 추가)

- `type` 에 `order_approval`, `fridge_inbound`, `cycle_paused` 추가. **컬럼 변경 없음**(값 추가이므로 CHECK 제약 여부에 따라 마이그레이션 필요 여부가 갈린다 — 인프라 확인 사항)

### 9-5. 마이그레이션 리스크 (데이터 검토관 기록)

| 항목 | 리스크 | 완화 |
|------|--------|------|
| `orders.status` CHECK 확장 | **낮음** — 기존 값 `confirmed` 는 새 집합에 포함되므로 기존 행 영향 없음 | 확장만, 축소 금지 |
| `orders.cycle_start` NOT NULL 추가 | **중간** — 기존 행 백필 필요 | 기존 행은 `confirmed_at::date` 로 백필. auto-order-p0 가 아직 미머지 상태라 프로덕션 데이터가 없다면 리스크 소멸 |
| 부분 유니크 인덱스 | **중간** — 백필 결과에 중복이 있으면 인덱스 생성 실패 | 생성 전 중복 검사 쿼리 선행. 운영 DB 는 `CONCURRENTLY` 검토 |
| `user_cycle_settings` 신규 | **낮음** — additive | 기존 사용자 행은 lazy 생성(첫 접근 시) 또는 백필 중 택1, 설계 확정 |
| partial index 스캔 성능 | **낮음** | `notification_settings` 에서 검증된 패턴 재사용 |

**총평**: 파괴적 변경 없음(전부 additive 또는 CHECK 확장). 유일한 주의점은 `cycle_start` 백필과 부분 유니크 인덱스의 순서다.

## 10. 비기능 요구사항

- **성능**: 사이클 스캔은 partial index 커버로 O(due 행). `GET /cycle` p95 < 300ms. 초안 생성은 네이버 순차조회+LLM 이 붙으므로 수 초~수십 초 허용(백그라운드 실행이라 사용자 체감 없음)
- **정확성**: 냉장고 재고와 주문 감산의 이름 매칭은 `name.strip().lower()` + **단위 일치**로 통일한다 (auto-order-p0 기술 제약 승계 — 현재 `fridge._matches` 에 `strip()` 누락)
- **신뢰성**: 푸시는 **보조 채널**. 미도달해도 웹/앱 화면에서 동일 정보를 확인·조작할 수 있어야 한다 (푸시 전용 흐름 금지 — app-webview-push 결정 승계). 자동확정은 푸시 도달 여부와 무관하게 동작하되, 그 사실을 설정 화면에 명시한다
- **멱등성**: 스케줄러의 모든 단계는 재실행 안전해야 한다 — 생성(주 1회 상한), 초안(사이클당 1건), 확정(부분 유니크), inbound(`inbound_at`)
- **관측성**: 사이클 단계 전이·스킵 사유(`skipped_dormant`/`deferred_quota`/`awaiting_user`/`expired`)를 구조화 로그로 남긴다. **개인정보·금액은 로그에 남기지 않는다**
- **접근성**: 사이클 상태 전이는 라이브 리전 통지. 승인 CTA 고지 텍스트는 색 단독 구분 금지. 자동확정 예정 시각은 텍스트로 명시
- **비용**: LLM 호출은 자동 생성 사용자당 주 1회 + 전체 일일 상한. 네이버 조회는 초안 생성 시 1회

주간 사이클의 모든 자동 실행(식단 생성, 초안 생성, 자동확정, 냉장고 등록)은 **서버 스케줄러가 수행**한다. 클라이언트가 백그라운드에서 깨어나 무언가를 할 필요가 전혀 없다. 이는 웹뷰 쉘 전략에 결정적으로 유리한 조건이다 — 앱은 **알림을 받고 화면을 여는 것**만 하면 되고, 그것이 정확히 얇은 웹뷰 쉘이 잘하는 일이다. 만약 자동화를 클라이언트에서 돌리는 설계였다면 네이티브 백그라운드 태스크가 필수였겠지만, 서버 사이드 설계 덕분에 그 요구가 사라진다.

## 12. 기술 제약사항

1. **스케줄러 인프라를 새로 도입하지 않는다** — `notification/scheduler.py` 의 lifespan asyncio + partial index 스캔 패턴을 재사용. APScheduler/Celery/Redis 도입 금지. `pyproject.toml` 확인 결과 현재 이런 의존성이 없으며, 추가하지 않는 것이 운영 부담상 유리
2. **단일 인스턴스 전제** — 현재 스케줄러가 그러하다. 멀티 인스턴스 배포 시 중복 실행이 발생하므로 **배포 형상 변경 시 반드시 설계 재소집**(분산 락 또는 리더 선출)
3. **비동기 식단 생성이 선행 조건** — 동기 생성 상태에서 스케줄러가 LLM 을 호출하면 이벤트 루프를 점유한다. `feature/app-webview-push` 의 202 전환 머지가 FR-804 의 전제
4. **auto-order-p0 머지가 선행 조건** — 본 기획은 `orders`/`order_items` 테이블과 preview/확정 로직 위에 컬럼과 상태를 얹는다
5. **이름 매칭 정합** — `fridge._matches` 의 `strip()` 누락을 order 집계와 함께 맞춘다. 이 변경은 식사완료 deduct 의 의미를 바꾸지 않는다
6. **`build_cart(mall)` 은 `kurly|all` 만 지원** — 자동 사이클도 KR 추정가는 `mall=kurly` 고정. 스토어별 전용 검색 어댑터를 만들지 않는다
7. **파트너 키 전제 기능 금지** — Walmart/Instacart/Apple 키가 필요한 기능은 이번 범위에 넣지 않는다
8. **정책 파라미터의 저장 위치** — 활성 판정 기준, 그레이스 시간, 미매칭 임계, 일일 상한, 스토어 리드타임, 임박 일수는 전부 **코드 상수가 아니라 조정 가능한 설정**으로 둔다. 환경변수 / 설정 테이블 중 어느 쪽인지는 설계 확정
9. **에이전트 관할** — `mobile/` 은 UI 프론트엔드 관할 확장(app-webview-push 결정). 본 기획은 `mobile/` 코드를 변경하지 않는다
10. **DDL 은 인프라 전담** — 리비전 번호 부여, 백필 순서, 부분 유니크 인덱스 생성은 인프라 에이전트가 수행

### 1라운드 — 🗂 PM

루프의 재료는 대부분 있다. main 에 식사완료→냉장고 차감(축3)까지 완결돼 있고, 자동주문(축2 후반)은 브랜치에 있으며, 알림·비동기·스케줄러 패턴도 브랜치에 있다. 빠진 것은 "연결"뿐이다 — 주간 롤링 자동 생성, 냉장고→식단 되먹임, 배송 시점 등록, 주기 설정, 예외 처리. 시간 축을 D-5(생성)/D-2(초안)/D-1(자동확정)/D(등록)로 잡고, 사용자 개입은 승인 1탭으로 압축한다. US-801~816 / FR-801~825.

### 2라운드 — 병렬 검토

**🔥 Devil's**
- "자동으로 돈 쓰는 시스템"을 만들면서 멱등을 P1 로 미뤄둔 게 최대 결함이다. 사람이 두 번 누르면 실수지만 스케줄러가 두 번 돌면 냉장고 인플레 + 이중 발주다 → **FR-816 으로 P0 승격**.
- 24h 그레이스 자동확정이 예산을 넘겨 버리면 제품의 핵심 약속(예산 락)이 깨진다 → **FR-812 게이트, 초과 시 자동확정 절대 금지**.
- 식사 완료 체크를 안 하는 사용자는 냉장고가 실제보다 가득 차 있다고 계산돼 다음 주문이 과소 발주된다 → 활성 판정(FR-802)에서 자연 탈락시켜 사이클을 멈추는 것이 옳다. 이걸 "버그"로 오해하지 않도록 문서화.
- 생성 실패 시 지난 주 식단을 연장하면 유효하지 않은 재료를 사게 된다 → 연장 금지(5-5).
- 오래된 초안이 뒤늦게 확정되는 문제 → `expired` 처리(4-3).
- US 는 추정가가 0 인데 자동확정할 근거가 뭔가 → **US 는 항상 사용자 승인**(FR-813).

**👤 UX**
- 승인 요청을 푸시로만 하면 웹 사용자는 영영 못 본다 → 홈 사이클 상태 카드(FR-824)가 인앱 대체 채널. 푸시는 보조 채널 원칙 유지.
- "냉장고에 담았어요"라고 단정하면 실제로 안 왔을 때 신뢰가 깨진다 → **"받으셨나요?"로 묻고 '아직'을 누르면 롤백**(5-3).
- 자동확정 예정 시각을 안 보여주면 사용자가 통제감을 잃는다 → 초안 화면에 "내일 09:00에 자동으로 확정돼요" 명시.
- 휴면 복귀자에게 밀린 알림을 쏟으면 그대로 이탈 → **소급 발송 금지, 1회 카드만**(FR-818).
- 개입 지점이 5개면 Zero-UX 라고 부를 수 있나 → 4개는 선택이고 실질 필수는 완료 체크 1개임을 4-4 로 명시.

**⚙️ 기술**
- 스케줄러를 새로 들이면 운영 부담이 는다. 브랜치의 lifespan asyncio + partial index 패턴이 이미 있고 의존성도 추가 안 했다 → 그대로 재사용.
- 동기 생성 상태로 스케줄러가 LLM 을 부르면 이벤트 루프를 막는다 → app-webview-push 의 202 전환이 선행 조건.
- 스케줄러가 사용자별로 같은 분에 몰리면 자기가 만든 rate limit 에 자기가 걸린다 → 지터 분산.
- inbound 는 `inbound_at` 으로 1회 보장. 재기동에도 냉장고가 두 번 차면 안 된다.
- `fridge._matches` 의 `strip()` 누락은 order 쪽과 함께 맞춰야 감산이 어긋나지 않는다.

**🔒 보안**
- CWE-602: 승인도 서버 재계산. 클라이언트가 preview 캐시로 확정하면 냉장고를 비운 척 조작 가능.
- CWE-639: **스케줄러도 user_id 스코프를 지켜야 한다.** 배치라는 이유로 전역 쿼리를 쓰면 그 자체가 IDOR.
- CWE-359: 푸시 본문에 금액·예산 금지. 잠금화면에 뜬다.
- CWE-841: 상태 머신을 명시하고 `confirmed → draft` 역행을 막아야 한다.
- CWE-367: 게이트 판정과 저장 사이에 사용자가 수동 확정할 수 있다 → DB 제약이 최종 방어선.
- 실결제 전환 시 자동확정을 그대로 켜두면 안 된다 → 별도 명시 동의·상한액·취소 기간을 실결제 기획 GATE 로 이관.

**🗄 데이터**
- `user_cycle_settings` 는 user 당 1행 UNIQUE + partial index. `notification_settings` 패턴 그대로.
- `orders.status` CHECK 확장은 기존 값을 포함하므로 안전. `cycle_start` NOT NULL 백필과 부분 유니크 인덱스는 **순서가 중요** — 백필 → 중복 검사 → 인덱스.
- `delivery_eta`/`inbound_at`/`auto_confirmed` 는 전부 additive.
- inbound 스캔용 partial index 필요.
- 로그에 금액·개인정보 금지.
